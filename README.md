# GuildGame

> **Unity 기반 2D 길드/전투 프로젝트**  
> 전투 FSM, 병사 관리, HP UI 동기화, Object Pool, TestScene 검증 흐름까지 포함해  
> **기능 구현 + 구조 설계 + 개선 관점**을 함께 정리한 포트폴리오용 프로젝트입니다.

## 프로젝트 소개

GuildGame은 **길드 운영과 전투 흐름을 중심으로 구성한 Unity 2D 프로젝트**입니다.  
단순히 전투 장면만 구현하는 데서 끝나지 않고,

- 씬 전환 흐름
- 전투 상태 제어(FSM)
- 병사(Soldier) 단위 관리
- HP/UI 동기화
- 반복 생성 오브젝트 관리
- TestScene 기반 검증

까지 함께 다루면서, **게임 기능이 늘어나더라도 구조가 버티는 형태**를 만드는 데 초점을 두었습니다.

이 프로젝트에서 특히 중요하게 본 포인트는 아래 두 가지입니다.

1. **전투 로직이 커져도 상태 관리가 무너지지 않도록 설계할 것**
2. **전투 로직, UI, 오브젝트 생성 흐름이 실제 플레이 중에도 어긋나지 않도록 동기화할 것**

---

## 핵심 기능

### 1. 전투 FSM 기반 상태 제어
전투 로직은 기능이 늘어날수록 입력 처리, 공격, 스킬, 피격, 사망, 타겟 탐색이 서로 엉키기 쉬운 영역입니다.

GuildGame에서는 이를 **FSM(State Machine) 기반으로 나누어 관리**하면서,
상태 전환의 책임을 명확히 하고 전투 기능이 확장되더라도 구조가 무너지지 않도록 정리했습니다.

핵심 의도는 아래와 같습니다.

- 상태별 책임 분리
- 전투 흐름 디버깅 난이도 완화
- 기능 추가 시 수정 범위 축소
- 캐릭터/병사 단위 동작 확장에 유리한 기반 확보

---

### 2. Soldier 중심 병사 관리 구조
병사 관련 시스템은 단순 생성만으로 끝나지 않습니다.

- 생성
- 상태 관리
- 전투 참여
- 타겟 탐색
- 체력 변화 반영
- 해제 및 재사용

까지 하나의 흐름으로 이어지기 때문에, 개별 병사 로직과 전체 병사 관리 로직이 섞이면 유지보수가 빠르게 어려워집니다.

GuildGame은 `Soldier`, `SoldierManager` 중심 구조를 통해
**개별 객체의 책임**과 **전체 전투 흐름 관리 책임**을 나누는 방향으로 구성했습니다.

이 구조는 이후 병사 종류가 늘어나거나 배치/소환/웨이브 구조가 복잡해질 때도 확장 가능한 기반이 됩니다.

---

### 3. HP UI 동기화
전투 프로젝트에서 실제 체력 값과 UI 표시가 어긋나는 문제는 자주 발생합니다.

GuildGame에서는 `UIManager`를 중심으로,
상태 변화가 발생하는 시점과 UI 갱신 시점을 최대한 일치시키는 방향으로 흐름을 정리했습니다.

이 과정에서 중요하게 본 부분은 아래와 같습니다.

- 전투 로직과 UI 로직의 책임 분리
- 병사 수 증가 시 UI 갱신 흐름 안정성 확보
- 상태 변화와 화면 반영 타이밍 일치
- 추후 이벤트 기반 UI 구조로 확장 가능한 형태 유지

---

### 4. Object Pool 기반 재사용 구조
전투/병사/이펙트가 반복 생성되는 게임에서는 `Instantiate`/`Destroy`가 누적되며 성능 부담으로 이어질 가능성이 큽니다.

GuildGame은 **Object Pool 구조를 고려한 흐름**을 정리하면서,
반복 생성이 많은 오브젝트를 재사용 가능한 형태로 관리하려는 방향을 잡았습니다.

이 구조의 장점은 아래와 같습니다.

- 반복 생성 상황에서 비용 절감
- 전투 중 생성/해제 타이밍 안정화
- 이후 이펙트, 투사체, 소환 오브젝트까지 확장 가능
- TestScene에서 반복 검증하기 쉬운 구조 확보

---

### 5. TestScene 기반 검증
게임 기능은 “작동한다”보다 **반복 상황에서도 안정적으로 유지되는지**가 더 중요합니다.

GuildGame은 `TestScene`을 별도로 두고,

- 병사 수 증가
- UI 갱신 반복
- 스킬 사용 반복
- 오브젝트 생성/재사용 반복

같은 상황을 확인하는 검증용 씬으로 활용했습니다.

이 씬은 단순 디버그용이 아니라,
**현재 구조가 실제로 버티는지 확인하는 테스트 환경**이라는 점에서 의미가 있습니다.

## 주요 씬 구성

### TitleScene
- 게임 시작 진입 씬
- 전체 플레이 흐름의 시작점

### LobbyScene
- 전투 진입 전 허브 역할
- 길드/캐릭터/준비 상태를 정리하는 구간

### LevelScene
- 레벨 단위 흐름 확인용 씬
- 전투 전후 상태 연결을 검증하는 구간

### StageScene
- 스테이지 진행 구조를 확인하는 씬
- 전투 단계와 라운드 흐름 검증에 활용

### BattleScene
- 핵심 전투 로직 검증 씬
- FSM, 병사, 스킬, 타겟 탐색, UI 반영 등을 확인하는 중심 구간

### CharacterScene
- 캐릭터 관련 상태/정보를 확인하는 씬
- 직업/캐릭터별 분기 구조 테스트에 활용

### TestScene
- 스트레스 테스트 및 반복 검증용 씬
- 병사 수 증가, 이펙트 생성, UI 갱신, 오브젝트 재사용 흐름 등을 점검

## 프로젝트에서 중요하게 본 설계 방향

### 1. 기능보다 흐름이 먼저 보이게 만들기
스크립트 수를 늘리는 것보다,
**어떤 씬에서 어떤 상태가 어떻게 다음 단계로 이어지는지**가 먼저 보이도록 구성하려고 했습니다.

### 2. 전투 로직과 UI 로직을 분리하기
전투 계산과 UI 갱신이 강하게 묶이면,
기능이 조금만 복잡해져도 수정 비용이 크게 늘어납니다.

그래서 상태 변화 → UI 반영 흐름을 나누고,
추후 기능을 추가하더라도 전체 구조가 흔들리지 않도록 정리했습니다.

### 3. 반복 생성되는 오브젝트는 재사용을 염두에 두기
병사, 이펙트, 전투 중 생성 오브젝트처럼 반복성이 높은 요소는
초기부터 Pool 관점으로 다루는 것이 유지보수에 유리하다고 판단했습니다.

### 4. 테스트 가능한 씬을 따로 두기
메인 씬 하나만으로 테스트를 반복하면 원인 파악이 어려워지는 경우가 많습니다.

그래서 TestScene을 별도로 두고,
기능을 빠르게 검증하고 문제를 재현하고 수정 후 다시 확인할 수 있는 흐름을 만드는 데 신경 썼습니다.

## 개선 포인트

현재 구조를 기준으로 이후 개선 가능하다고 판단한 부분도 함께 정리했습니다.

- 타겟 탐색 결과에 대한 **null 체크 보강**
- `Find`, `GetComponent`, `Physics` 계열 호출 구간의 **비용 최적화**
- `LayerMask` 활용 강화
- 싱글톤 초기화 시점을 `Awake()` 기준으로 더 명확히 관리
- 병사/이펙트 관련 **Pool 적용 범위 확장**
- 느슨한 데이터 구조를 **강타입 구조로 전환**
- UI 갱신을 이벤트 기반으로 더 정리

이 프로젝트는 단순히 결과물만 보여주기보다,
**어떤 부분이 아직 개선 가능하고 왜 그렇게 판단했는지**까지 드러내는 포트폴리오로 정리하고자 했습니다.

## 회고

GuildGame을 정리하면서 가장 중요하게 느낀 부분은,
게임 기능 하나를 구현하는 것보다
**여러 시스템이 동시에 돌아갈 때도 구조가 유지되도록 만드는 것**이 훨씬 어렵고 중요하다는 점이었습니다.

특히
- 전투 FSM
- 병사 관리
- UI 동기화
- Object Pool
- 테스트 씬 운영

같은 요소들은 각각 따로 보면 작은 기능처럼 보일 수 있지만,
실제로는 서로 영향을 많이 주기 때문에
초기에 구조를 어떻게 잡느냐가 전체 완성도에 큰 차이를 만든다고 느꼈습니다.

이 프로젝트는 그런 점에서,
**기능 구현 능력뿐 아니라 구조화, 테스트, 개선 관점까지 함께 보여줄 수 있는 작업물**로 정리하고 있습니다.
